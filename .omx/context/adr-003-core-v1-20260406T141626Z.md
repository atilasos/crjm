# Context Snapshot — ADR-003 core V1

- **Task statement:** Clarificar ADR-003 do CRJM vNext para fechar o núcleo V1 canónico persistente, sem perguntar ao humano o que já pode ser inferido com boa confiança do repositório.
- **Desired outcome:** Um brief executável que feche entidades mínimas, fronteira de V1, exclusões explícitas e invariantes pedagógicas para o modelo de dados/API.
- **Stated solution:** Brownfield deep-interview orientado por evidência local: `docs/agents/reviews/crjm-vnext-direction.md`, `crjm-vnext-adr-001.md`, `crjm-vnext-adr-002.md`, `docs/agents/PEDAGOGY-MODEL.md`, `docs/agents/PEDAGOGY-GAMIFICATION.md`, `src/components/gamification/*`, `src/ai-core/*`, `src/App.tsx`, `src/server/*`, `src/tournament/*`.
- **Probable intent hypothesis:** Congelar o mínimo canónico persistente do vNext para que a V1 saia com autenticação + progresso por aluno semanticamente correto, sem arrastar já o escopo de histórico completo, turma/professor ou compute forte.

## Known facts / evidence

1. `crjm-vnext-direction.md` redefine o CRJM atual como baseline/protótipo e abre vNext backend-first com auth, progresso persistente por aluno e IA mais fiável.
2. `crjm-vnext-adr-001.md` fixa arquitetura React + backend API + Postgres e separa frontend, identidade/progresso/sessões e engines.
3. `crjm-vnext-adr-002.md` fixa stack (Hono+Bun, Postgres, Drizzle, Supabase Auth) e recorta V1 como: auth funcional, utilizador/aluno, progresso persistente por jogo, dashboard básica do aluno.
4. O estado atual persistido no produto é local (`localStorage`) via `GamificationProvider` + `gamification-state.ts`, com `GamificationProfile` contendo: XP total, XP de sessão, streak, achievements, `gameProgress` por jogo e `recentEvents` (`game_completed`, `review_completed`).
5. `PEDAGOGY-MODEL.md` e `PEDAGOGY-GAMIFICATION.md` deixam claros invariantes: aprendizagem > vitória; revisão pós-jogo é nuclear; progresso é pessoal (sem leaderboard global por defeito); hints/tutor são scaffold e não substituto da reflexão.
6. O produto atual já expõe 6 jogos, perfil/progresso, tutor e campeonato, mas o modo campeonato usa entidades próprias e não constitui ainda o núcleo persistente pedagógico do aluno.
7. `crjm-vnext-adr-002.md` empurra histórico de partidas/turning points/achievements persistentes para V2 e turma/professor para V3.

## Constraints

- Foco em **V1 canónico persistente**.
- Não fazer implementação de produto; apenas clarificação/artefacto de requisitos.
- Reaproveitar semântica já validada do protótipo atual em vez de reinventar o modelo.
- Não pedir perguntas desnecessárias ao humano.
- Preservar coerência com AE/MEM/ZPD já documentadas.

## Unknowns / open questions

- Se V1 precisa armazenar apenas agregados pedagógicos ou também um log mínimo de eventos para recomputar streaks/missões/achievements.
- Se preferências do aluno (ex.: nome visível, ciclo etário, dificuldade default) entram já no perfil V1 ou ficam opcionais.
- Se achievements devem ser materializados como unlocks persistidos ou derivados sob demanda.

## Decision-boundary unknowns

- OMX pode decidir a granularidade mínima do log (`activity_events`) desde que não reintroduza histórico completo de partida.
- OMX pode decidir se achievements/missões são derivados ou parcialmente materializados, desde que a semântica pedagógica atual seja preservada.
- OMX não deve puxar turma/professor/matches/reviews completas para V1 sem confirmação explícita, porque os ADRs já os empurram para fases seguintes.
